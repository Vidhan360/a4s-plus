# A4S+ — Machine learning

> **The single most important sentence in this document.** The models below are
> trained on synthetic data produced by this repository's own simulation
> engine, and their labels come from this repository's own rule engine. Every
> metric quoted here is genuinely measured on a held-out, subject-disjoint
> split of that synthetic data. **None of it is clinical evidence.** The models
> are not clinically validated, have never seen a real physiological recording,
> and must not inform a decision about a human being.

## 1. The problem, stated precisely

**Task.** Given the last 24 one-minute feature vectors for one person, predict
their **rule-engine risk category 30 simulated minutes later**, as a 4-class
problem over `LOW, MODERATE, HIGH, CRITICAL`.

**Why that framing.** It is the strongest honest claim available. A model
trained on simulated vitals cannot learn to diagnose acute mountain sickness.
It *can* learn to anticipate a deterministic scoring function earlier than the
function itself would fire — which is exactly the product claim: *detection →
prediction → prevention*. The rule engine detects; the model buys warning time.

**Derived metric.** Operationally, the question is "is this person about to be
in trouble?", so every model also reports a binary **elevated-risk** score:
`HIGH or CRITICAL` versus `LOW or MODERATE`.

## 2. Dataset

Generated by `ml/dataset.py`, which drives the same `VitalsSimulator` and
`EnvironmentModel` the live application uses — so training data and runtime
data come from one process, not two.

| Property | Value |
|---|---|
| Subjects | 480 |
| Steps per subject | 190 (1 simulated minute per step) |
| Window length | 24 steps |
| Horizon | 30 minutes (30 steps) |
| Classes | LOW, MODERATE, HIGH, CRITICAL |
| Split | **grouped by subject** — 70 / 15 / 15 train / val / test |
| Seed | 20260909 |
| Provenance tag | `SYNTHETIC_SIMULATION` |
| Scenario mix | NORMAL 118 · GRADUAL_DETERIORATION 115 · ALTITUDE_STRESS 101 · ACUTE_EVENT 97 · RECOVERY 49 |
| Test windows | 9 864 (learned models) / 4 932 (rule baseline, evaluated on every 2nd window) |

**Subject-disjoint splitting is the point.** Consecutive windows from one
person overlap by 23 of 24 steps. A random split would put near-duplicates on
both sides of the wall and inflate accuracy dramatically. Splitting by subject
means the test set contains people the model has never seen.

Class imbalance is handled by inverse-frequency weights in the loss rather than
by resampling, so the reported confusion matrix reflects the true class
distribution.

## 3. Features (16)

`ml/features.py` is the single feature definition, imported by training,
evaluation *and* live inference — there is no second copy that can drift.

| Group | Features |
|---|---|
| Physiological (8) | `heart_rate`, `spo2`, `body_temp_c`, `respiratory_rate`, `bp_systolic`, `bp_diastolic`, `altitude_m`, `fatigue_score` |
| Environmental (2) | `env_temp_c`, `wind_kph` |
| Activity (1) | `exertion` (ordinal encoding of activity level) |
| First differences (5) | `d_heart_rate`, `d_spo2`, `d_respiratory_rate`, `d_altitude_m`, `d_fatigue_score` |

The deltas exist because rate of change carries the signal a snapshot cannot:
SpO₂ of 88 % that has been stable for an hour is a different situation from
SpO₂ of 88 % that was 96 % ten minutes ago.

Standardisation uses the **training split's** mean and standard deviation. Both
vectors are saved in the artifact's `metadata.json` and re-applied verbatim at
inference, so a production prediction is scaled exactly as training was.

## 4. Models

### 4.1 Rule baseline — the number everything must beat

`ml/baseline.py`. A **persistence forecast**: the rule engine's current category
is used as the prediction for t+30. Zero trainable parameters.

This is deliberately the hardest honest baseline to beat, because vitals are
autocorrelated — "nothing will change in the next half hour" is right most of
the time. A model that cannot beat persistence has learned nothing.

### 4.2 LSTM — the sequence model

`ml/model.py`, PyTorch, **125 029 parameters**:

```
input  (batch, 24, 16)
  → LSTM(hidden=96, layers=2, dropout=0.25, unidirectional)
  → attention-weighted temporal pooling   (Linear(96→1) → softmax over time)
  → LayerNorm(96)
  → Linear(96→64) → GELU → Dropout(0.25)
  → Linear(64→4)  → logits over (LOW, MODERATE, HIGH, CRITICAL)
```

Attention pooling instead of "take the last hidden state" for two reasons:
deterioration often begins partway through a window, and the attention weights
are a genuinely computed second explanation signal that can be surfaced without
inventing anything.

**Training** (all recorded in the artifact):

| | |
|---|---|
| Optimiser | AdamW, lr 2e-3, weight decay 1e-4 |
| Loss | CrossEntropy with inverse-frequency class weights |
| Batch | 256 |
| Scheduler | ReduceLROnPlateau(factor 0.5, patience 2) |
| Gradient clipping | max-norm 1.0 |
| Early stopping | patience 6 on validation macro-F1 |
| Epochs | 30 requested, **9 run, best at epoch 3** (early stopping fired) |
| Seed | 20260909 (Python, NumPy and Torch all seeded) |
| Device | CPU |

Early stopping at epoch 3 is itself a finding, reported rather than hidden: the
synthetic generative process is learnable quickly, and further epochs overfit
the simulator's noise model.

### 4.3 Gradient boosting — the tabular comparator

`sklearn.ensemble.HistGradientBoostingClassifier`, lr 0.08, `max_depth=7`,
`max_iter=220`, early-stopped at **181 iterations**, trained in 17.3 s.

Trees cannot consume sequences, so each of the 16 channels is summarised over
the window by **last, mean, min, max and net change** → 80 tabular features.
Level *and* trend information is preserved, so the comparison is fair rather
than a straw man.

## 5. Measured results

Held-out, subject-disjoint synthetic test split. Reproduce with
`python -m ml.train --subjects 480 --epochs 30`; artifacts and the comparison
JSON are written under `ml/artifacts/`.

### 5.1 Headline

| Model | Accuracy | Macro P | Macro R | Macro F1 | Weighted F1 |
|---|---|---|---|---|---|
| Rule baseline | 0.7474 | 0.7601 | 0.6811 | 0.7024 | 0.7415 |
| LSTM | 0.8913 | 0.8619 | 0.9027 | 0.8770 | 0.8919 |
| **Gradient boosting** | **0.9142** | 0.9005 | 0.9048 | **0.9024** | 0.9143 |

### 5.2 Elevated risk (HIGH/CRITICAL vs LOW/MODERATE)

| Model | Precision | Recall | F1 | ROC AUC | Brier | FN |
|---|---|---|---|---|---|---|
| Rule baseline | 0.8715 | 0.7604 | 0.8122 | — | — | 483 / 2 016 |
| LSTM | 0.9392 | 0.9322 | 0.9357 | 0.9913 | 0.0370 | 274 / 4 041 |
| **Gradient boosting** | 0.9313 | **0.9587** | **0.9448** | **0.9925** | **0.0363** | **167 / 4 041** |

### 5.3 Per class, LSTM

| Class | Precision | Recall | F1 | Support |
|---|---|---|---|---|
| LOW | 0.9782 | 0.9639 | 0.9710 | 3 488 |
| MODERATE | 0.8344 | 0.8634 | 0.8487 | 2 335 |
| HIGH | 0.9049 | 0.8054 | 0.8523 | 3 120 |
| CRITICAL | 0.7301 | **0.9783** | 0.8362 | 921 |

The CRITICAL column is the interesting one, and it is the shape you want from a
safety system: recall 0.978 with precision 0.730 means the model catches
essentially every critical case and pays for it with false alarms. That
asymmetry was produced by the class weighting, not selected after the fact.

### 5.4 The result we are not hiding

**Gradient boosting beat the LSTM** on accuracy (0.9142 vs 0.8913), macro F1
(0.9024 vs 0.8770), elevated-risk F1 (0.9448 vs 0.9357), ROC AUC and Brier
score. It also trains in 17 seconds and needs no GPU.

Why that is plausible: 24-step windows summarised by five statistics retain
almost all of the signal in a *smooth, low-dimensional, synthetic* process, and
tree ensembles are extremely strong on small tabular problems. The sequence
model's advantage — modelling long, irregular temporal structure — is largely
unavailable because the simulator's dynamics are gentle and short-memory.

Why the LSTM remains the default anyway, stated as a judgement rather than a
result:

1. It is the architecture that would benefit from real, noisy, irregularly
   sampled sensor data, which is the direction the project is heading.
2. Its explanations are per-timestep, which is what the "WHY THIS RISK?" panel
   needs to say *when* the trend turned.
3. Both learned models are available at runtime and comparable in the UI, so
   the choice is visible and reversible with one config change
   (`A4S_ML_ACTIVE_MODEL`).

If this were a product decision rather than a prototype, the honest answer
would be: ship the gradient booster, and keep the LSTM in research until real
sensor data exists to justify it.

## 6. Explainability — only what is actually computed

Each model reports the method it genuinely uses. **SHAP is not used anywhere,
and no SHAP values are displayed.**

| Model | Method | What it computes |
|---|---|---|
| Rule baseline | `TRANSPARENT_WEIGHTS` | The engine's own factor weights and threshold distances — exact, not an approximation |
| LSTM | `OCCLUSION_SENSITIVITY` | For each of the 16 channels, replace it across the window with its training mean, re-run the forward pass, and measure the change in the elevated-risk logit. 16 extra forward passes per explanation. |
| Gradient boosting | `IMPURITY_IMPORTANCE` | Split-impurity importance, aggregated from the 80 flattened features back to the 16 base channels. Permutation importance is also computed at training time and stored in the artifact. |

Each method's limitations are returned by `GET /predictions/methods` and shown
in the UI: occlusion is a single-feature ablation and therefore blind to
interactions between channels; impurity importance is global to the model, not
local to the individual prediction; transparent weights only explain the rule
engine, which is not the model that made the prediction.

The `narrative` field is generated from the computed contributions by a
template — it is prose *about* real numbers, never a substitute for them.

## 7. Versioning and serving

```
ml/artifacts/
├── last_comparison.json                 the measured comparison the UI reads
├── lstm/v20260909-100649/
│   ├── model.pt                         weights
│   ├── metadata.json                    config, scaler, hyperparameters,
│   │                                    metrics, provenance, disclaimer
│   └── training_history.json            per-epoch loss and validation F1
└── gradient_boosting/v20260909-100711/
    ├── model.joblib
    └── metadata.json
```

`ml/registry.py` discovers versions on disk, loads the newest per model,
validates that the artifact's feature list matches the code's feature list, and
**refuses to serve a model whose features have drifted** rather than silently
mis-scaling inputs. `POST /api/v1/predictions/reload` swaps in a newly trained
version without a restart.

Every stored prediction row records `model_name`, `model_version`,
`explanation_method`, `data_provenance`, `sequence_length` and `inference_ms`,
so any historical number can be traced to the exact artifact that produced it.

## 8. Inference path

1. Load the last 24 readings for the person, ordered by `recorded_at`.
2. **Fewer than 24?** Return an explicit insufficient-history response. No
   padding, no extrapolation, no guess.
3. Build the 16-channel matrix with the same `ml/features.py` used in training.
4. Standardise with the artifact's saved mean/std.
5. Forward pass → softmax over 4 classes; elevated probability = P(HIGH) +
   P(CRITICAL).
6. Compute contributions with the model's own method.
7. Persist, publish on the `vitals` topic, return with timing.

Measured single-window CPU latency is a few milliseconds and is reported per
call as `inference_ms`, rather than quoted as a claim here.

## 9. Testing the ML code

`backend/tests/unit/test_ml_*.py` runs against the real network with no mocks:
feature construction and ordering, scaler round-tripping, sequence windowing,
the subject-disjoint split invariant, registry version selection and
feature-drift rejection, occlusion attribution shape and sign, and a genuine
short training run that asserts the loss actually decreases. That last test is
small so it stays fast, but nothing in it is faked — a real optimiser runs real
gradients.

## 10. What would make these numbers mean more

1. Real physiological recordings — without them, the metrics describe the
   simulator, not the physiology.
2. Labels from clinical outcomes rather than from our own rule engine, which
   currently caps how much the model can add.
3. Cross-validation across multiple simulator seeds and generative
   configurations, to separate learning the task from learning one process.
4. Calibration analysis (reliability diagrams) beyond the Brier score.
5. Prospective evaluation: does the earlier warning actually change an outcome?
   That is the only question that matters for prevention, and this prototype
   cannot answer it.
